# 旧版 AI 解读单次点击升级设计

## 目标

修复旧版已完成记录在缺少云端 `readingId` 时，第一次点击“生成新版综合卦象解读”只恢复云端编号、第二次点击才真正生成新版内容的问题。修复后，用户只需点击一次，客户端就在同一流程中恢复云端编号并强制生成含 `comprehensive_hexagram_reading` 的新版 AI 解读。

## 根因

`src/cloud/sync-manager.js` 的 `retryRecord()` 对有 `readingId` 的旧记录会调用带 `{ force: true }` 的重试接口；但对没有 `readingId` 的旧记录只执行 `queue()` 和 `flush()`。当服务端通过幂等键命中旧的已完成记录时，创建接口会返回旧版结果并补回 `readingId`，客户端随即结束流程，因此页面仍然显示旧版内容。

## 修复流程

1. `retryRecord()` 使用可更新的当前记录变量。
2. 若初始记录没有 `readingId`，先执行现有的入队与同步流程。
3. 同步后重新读取本地记录，取得服务端恢复的 `readingId` 和最新 AI 状态。
4. 如果最新状态不是“已完成的旧版解读”，直接返回，不额外请求。
5. 如果最新状态为 `completed` 且缺少 `comprehensive_hexagram_reading`，立即调用重试接口，并传入 `{ force: true }`。
6. 保存强制重试返回的新版结构并通知界面刷新。

## 边界与兼容性

- 已有 `readingId` 的旧版记录继续直接强制升级。
- 新建后已经返回新版综合解读的记录不重复调用重试接口。
- 新建后仍处于排队、失败或拒绝状态的记录保持现有状态，不错误触发强制升级。
- 排盘、问题、起卦输入和本地解读均不改变。
- 网络失败仍沿用现有上传队列与错误状态处理。

## 验收标准

- 缺少 `readingId` 的旧版已完成记录，单次调用 `retryRecord()` 会先调用 create，再调用 retry。
- retry 的第三个参数严格为 `{ force: true }`。
- 本地最终保存 `comprehensive_hexagram_reading`。
- 现有同步、失败重试和已有云端编号升级测试全部通过。
- 完整测试与生产构建通过。
